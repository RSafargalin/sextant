## Как сообщить об уязвимости

Пожалуйста, сообщайте о проблемах безопасности через приватный механизм GitHub (вкладка
«Security» → «Report a vulnerability»), а не публичным issue.

Первый ответ — в течение 7 дней. Программы вознаграждений нет.

## Модель угроз — прочтите до того, как запускать sextant на коде, которому не доверяете

sextant — локальный инструмент разработчика. У него нет сетевой поверхности, нет серверной
части, доступной снаружи машины, и нет собственной аутентификации. Значимая для безопасности
поверхность — это то, что он **выполняет** и что **пишет**.

### `sextant index` выполняет сборку целевого проекта

Это самое важное, что нужно знать. Чтобы получить семантический индекс Swift, нужно запустить
систему сборки проекта:

- `swift build --enable-index-store` **выполняет `Package.swift` целевого проекта**, а это
  произвольный Swift-код, плюс любые объявленные им SwiftPM- и build tool-плагины.
- `sextant index --app` вызывает `xcodebuild`, который **выполняет build phases проекта**,
  включая фазы «Run Script».

Это свойство платформы, а не дефект sextant: получить семантический индекс без компиляции кода
невозможно. Следствие конкретное:

> **Запуск `sextant index` на недоверенном репозитории эквивалентен запуску сборки этого
> репозитория. Не делайте этого вне песочницы.**

Что сделано для смягчения:

- `index` печатает предупреждение о том, что выполнит манифест проекта.
- MCP-сервер **отказывается запускать сборки**. `--reindex` через MCP или демон отклоняется,
  поэтому агент не может вызвать сборку побочным эффектом запроса. Сборка индекса — явное
  действие человека в CLI.
- Все остальные команды (`map`, `api`, `search`, `lint`, `changed` и все семантические запросы)
  только *читают*: исходники, индекс git и уже существующий index store. Ни одна из них не
  компилирует.

Пока не сделано: запуск сборки в ограниченном окружении (`sandbox-exec` или очищенный env).
Это записано в работы по операционной зрелости; до тех пор действует предупреждение выше.

### Локальный демон (`sextant serve`)

`serve` слушает unix-сокет в кэш-каталоге пользователя, по одному на проект. Права unix-сокета
означают, что запросы к нему может слать любой процесс того же пользователя — та же граница
доверия, что и у его шелла. По сети он недоступен. Демон сверяет присланный клиентом корень
проекта со своим, поэтому заставить его отвечать по другому проекту нельзя.

### Что sextant пишет

- Index store и база IndexStoreDB: `~/Library/Caches/sextant/`
- Кэши парсинга и деклараций по content-hash: тот же кэш-каталог
- Конфиг проекта: `.sextant.json` в корне, пишется только командой `sextant init`
- Регистрация MCP: `.mcp.json` в корне, пишется только `sextant init`, с сохранением уже
  зарегистрированных там серверов

В ваши исходники sextant не пишет никогда.

### Телеметрия

Только opt-in и только локально. Никуда ничего не отправляется, эндпоинта не существует. В
локальный файл пишутся имена команд, длительности и статус выхода — чтобы решения по роадмапу
принимались по замерам, а не по догадкам. По умолчанию выключена.

### Обработка недоверенного ввода

sextant парсит исходники через SwiftSyntax и читает index store, произведённые Swift-тулчейном.
Ожидаемая реакция на некорректный ввод — ошибка или явно помеченный неполный результат, но
никогда не тихий неверный ответ: это то самое свойство «громкой деградации», вокруг которого
инструмент построен. Если вы нашли ввод, на котором sextant выдаёт уверенный, но неверный
результат, — это баг, о котором стоит сообщить, даже если он не связан с памятью.
