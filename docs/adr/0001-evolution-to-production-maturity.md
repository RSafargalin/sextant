# ADR-0001: Эволюция sextant к продакшн-зрелости

- **Статус:** Принято направление (реализация поэтапно, каждый шаг за гейтом после серии реальных тестов)
- **Дата:** 2026-06-29
- **Автор:** Руслан Сафаргалин
- **Связано:** `docs/roadmap.md` (итерации Iter 0–3)

## Контекст

sextant (v0.5.13) функционально полон по основной миссии — заменить `grep` при навигации
по Swift-коду. Инструмент установлен, подключён к двум реальным проектам (A и Б). На реальных
замерах навигация по символам дешевле grep на **80–99% токенов** (проект A: 5 запросов
2148 vs 51023 ток; проект Б `SomeScreen`: 298 vs 66807 ток — grep растёт линейно с числом
совпадений, sextant-сводка почти константна).

Честная оценка вскрыла, что до **зрелого продакшн-решения** не хватает не возможностей, а
качеств:

- **Тихая неправота (silent-wrongness)** — главный риск. Неполный/пустой семантический
  ответ выглядит правдоподобно правильным. У grep провал виден (простыня), у sextant —
  невидим. Агент, доверяющий неверному ответу, хуже агента с grep.
- **Хрупкость свежести индекса** — семантика требует собранного и свежего index store;
  на активном проекте он дрейфует, пересборка через xcodebuild — минуты. На проекте Б индекс был
  устаревшим.
- **Swift-only** — упирается в «переиспользуемость на всех проектах».
- **Кросс-worktree баг** — единый DerivedData-стор накапливает index-units из соседних
  worktree; `isProjectSource` их не отсекает → ложные дубли в `refs`.

Цель ADR — зафиксировать стратегию доведения sextant до продакшн-зрелости и каталог идей,
накопленных в брейншторме 2026-06-29.

## Решение

Принимается многоуровневая программа развития. Реализация — поэтапно, каждое направление
за **гейтом**: без подтверждённой на реальных тестах пользы дальше не идём.

**Сквозной архитектурный принцип.** «Кардинально новое» — это не десятки фич, а **2–3
фундаментальных слоя**, поверх которых фичи появляются почти бесплатно:

1. **Content-hash дайджест графа** — производный, query-optimized кэш над IndexStoreDB,
   ключуется по хэшу контента (не mtime). Worktree-safe, инкрементальный.
2. **Протокол сессии** — stateful-память о том, что уже отдано конкретной сессии агента.
3. **Надёжность/provenance** — каждая запись/ответ знает свою свежесть и происхождение.

Эти три слоя разблокируют дифф-контекст, prefetch, зону памяти, громкую stale-деградацию и
context-compiler одновременно.

---

### Направление 1 — Надёжность и доверие (приоритет: фундамент)

Закрыть silent-wrongness. Без этого «лучшим» инструмент не станет.

- **Provenance в каждом ответе** — пометка источника: свежий индекс / устаревший /
  синтаксический fallback.
- **Громкая деградация** — stale-индекс не молчит: предупреждение в выводе или отказ с
  actionable-подсказкой, а не правдоподобно-неполный результат.
- **Cross-check** — семантику сверять со структурным слоем: «индекс: 3 ссылки; grep `Foo(`
  находит 7 — вероятно стейл». Расхождение = флаг.
- **Golden-set харнесс** — зафиксированные `символ → ожидаемые refs` на двух реальных проектах,
  гоняется в CI; ловит молчаливые регрессии (которых в истории много).

### Направление 2 — Оптимизация и эффективность

Две разные «эффективности»: **машинная** (латентность, RSS, throughput) и **токенная**
(сколько контекста агента съедает ответ). Для LLM-инструмента токенная важнее — конвертируется
в деньги и в потолок задачи.

| # | Оптимизация | Механизм | Эффект |
|---|---|---|---|
| A1 | Cold-старт CLI | демон `sextant serve` + unix-socket, CLI = тонкий клиент с тёплым индексом | 2.1с→0.2с все вызовы, не только MCP |
| A2 | Латентность запроса | мемоизированный in-memory `name→[USR]` индекс | повторные lookup O(1) |
| A3 | Обход на масштабе | `git ls-files` вместо FileManager.enumerator | C-скорость, полный gitignore, **попутно чинит кросс-worktree** |
| A4 | Кэш парсинга | persistent sidecar `content-hash→декларации` (НЕ mtime — хрупок к checkout/worktree/stash) | `map`/`lint`/`search`: O(все)→O(изменённые); lint 14с→<1с |
| A5 | Токенная эффективность | адаптивная многословность (MCP компакт/TTY читаемо); **гистограмма вместо списка**; дедуп; детерминированный порядок → prompt-cache модели | прямой выигрыш в главной метрике |
| A6 | Стоимость индекса | SPM-only путь; частичная свежесть по timestamps юнитов | реиндекс только изменённых модулей |
| A7 | Query digest | mmap «дайджест проекта» (символьная таблица + граф ссылок плоско); запрос = pointer-chasing | снимает латентность открытия И запроса; worktree-safe |
| A8 | `sextant bench` | фиксированный набор запросов → p50/p95, peak RSS, **счётчик токенов вывода**; в CI | ловит перф-регрессии; фундамент дисциплины |

**Синергия:** A3+A4+A7 все ключуются на content-hash и одновременно дают скорость +
инкрементальность + фикс кросс-worktree. Одно архитектурное решение, не три задачи.

### Направление 3 — Кардинально новые возможности (смена природы инструмента)

1. **Дифференциальный контекст (session-aware)** — sextant помнит, что отдал этой сессии;
   повторный запрос неизменного символа → «не изменился с хода N» (~5 ток) или дельта.
   Убивает самую частую трату токенов в долгих сессиях. Stateless→stateful.
2. **Инверсия в retrieval-слой** — вход = описание задачи, выход = готовый ранжированный
   token-budgeted context-pack с цитатами. Агент перестаёт искать. Высший потолок ценности.
3. **Всегда-свежий индекс через build-hook** — Swift build plugin / xcodebuild post-action
   обновляет индекс как побочный эффект обычной сборки. Свежесть бесплатна; убивает stale в корне.
4. **Graph-RAG** — эмбеддинги по именам+doc, заземлённые на граф символов (вектор находит
   кандидата → граф даёт точные связи). Поиск по смыслу без точного имени.
5. **Сервис верификации** — агент шлёт утверждение («у X нет других вызывающих»), sextant
   возвращает вердикт + уверенность + доказательства. Из «отвечалки» в fact-checker; закрывает
   риск тихой неправоты.
6. **Семантический рефакторинг-as-a-service** — не только найти call-sites, но предложить
   проверенный диф (rename через protocol-dispatch, смена сигнатуры). Read-tool → safe-write-tool.
7. **Спекулятивный prefetch** — на `context Foo` прогревать соседей по графу и прикладывать
   «вероятно понадобится». Меньше round-trip’ов.
8. **Кросс-проектный интеллект** — единый индекс над всеми проектами разработчика;
   «где этот протокол реализован во всех репозиториях».

### Направление 4 — Зона памяти (code-anchored memory tier)

Внешняя память, разгружающая контекстное окно агента. **Тезис, отличающий её от опасной
generic-памяти агента:** она привязана к коду (content-hash) и **авто-инвалидируется** —
меняется код, запись помечается stale, а не отдаётся молча. Дополняет (не дублирует)
файловую `MEMORY.md`: та — человеко-проектные факты, эта — выводимые из кода, само-протухающие.

**Пять трактовок (берём лучшее из каждой):**

- **A. Память-по-указателю** — sextant возвращает стабильный хэндл `ctx://symbol@hash`
  (~10 ток) вместо блоба; полный контекст в зоне памяти. Пейджинг контекста: окно держит
  индекс указателей, не данные.
- **B. Кэш производного знания** — дорогие деривации (call-граф, blast-radius, карта фичи)
  считаются раз, ключуются по content-hash, живут cross-session/cross-agent.
- **C. Сессионный scratchpad** — заметки/выводы агента наружу по ссылке (помечены как
  `asserted`, не ground-truth).
- **D. Дистилляция рабочего набора** — всегда-актуальное саммари для **регидратации после
  компакции контекста**: точная замена лоссовому сжатию.
- **E. Cross-session база знаний проекта** — долговечные code-anchored факты
  (entry-points, границы модулей). Институциональная память кодовой базы.

**Как разгружает окно:** хэндлы вместо блобов; дельты; саммари + drill-down; регидратация
после компакции.

**Архитектура:** anchoring (запись ↔ content-hash, изменение → loud-stale); адресация
(хэндлы `ctx://symbol@hash`); тиринг (hot сессия / warm проект / cold cross-project);
eviction LRU+релевантность под бюджет; provenance/confidence (`derived` верифицируемо vs
`asserted` гипотеза — **asserted никогда не маскируется под ground-truth**). Поверхность
реализации — **MCP resources** (чтение по URI + подписки на обновление «запись протухла»).

### Направление 5 — Мультиязык (tree-sitter)

ObjC (в проекте Б есть interop) + generic структурный слой для любого языка. `search`/`lint`
обобщаются даже без семантики. Разблокирует не-Swift проекты — превращает
Swift-утилиту в кросс-проектный продукт.

### Направление 6 — DX, дистрибуция и adoption-механика

`sextant init` (детект типа проекта → индекс → `.mcp.json` → регистрация MCP одной командой);
prebuilt-бинарь / Homebrew (убрать 8-минутную сборку из онбординга).

**Наблюдение (2026-06-29): adoption ломается не на возможностях, а на привычке.** В этой же
сессии агент, который знает про sextant и у которого инструмент подключён через MCP, по
умолчанию тянулся к `grep`/`find` в нескольких местах, где семантический эквивалент лёг бы
лучше. Это не разовая оплошность, а системный сигнал: **наличие инструмента не равно его
использованию**. Прямое следствие для продукта — adoption нужно проектировать, а не
предполагать:

- **Тюнинг описаний MCP-инструментов** под модель (буквально prompt-engineering tool-descriptions):
  когда агент выбирает `grep` вместо `context`, проблема часто в формулировке описания.
- **Перехват/подсказка.** Когда агент в Swift-проекте с готовым индексом ищет символ через
  `grep` — sextant (или hook) мог бы мягко предлагать семантический эквивалент. Превращает
  привычку из тихого «промаха adoption» в обучающий момент.
- **context-compiler / retrieval-инверсия** (Направление 3) закрывает это радикально — убирает
  у агента сам выбор «чем искать».

Метрика adoption (доля символьных поисков, прошедших через sextant, а не grep) должна попасть
в opt-in телеметрию и в `bench` — иначе «лучший инструмент» останется неиспользуемым.

## Последовательность (по leverage/cost)

1. **`bench` (A8) + golden-eval (Направление 1)** — измерительный фундамент. Без него
   остальное вслепую: нельзя оптимизировать неизмеряемое, нельзя ловить молчаливые регрессии.
2. **content-hash кэш (A4) + `git ls-files` (A3)** — крупнейший машинный выигрыш, попутно
   чинит worktree-баг и mtime-хрупкость.
3. **демон `serve` (A1)** — убирает cold-старт для CLI.
4. **Токенная эффективность (A5)** — гистограммы + адаптивная многословность. Дёшево, прямой выигрыш.
5. **digest (A7) → зона памяти → мультиязык → context-compiler** — большие слои, по гейтам.

## Последствия

**Плюсы.** Программа превращает sextant из «обёртки над grep» в trustworthy-by-default
подсистему извлечения и памяти агента. Сквозные слои дают высокую синергию — одно решение
закрывает несколько проблем.

**Риски и издержки.**
- **Рост сложности.** Stateful-сессия + зона памяти + демон — это уже не утилита, а
  подсистема с жизненным циклом. Существенный шаг по поддержке.
- **Инвалидация — make-or-break.** Зона памяти и любой кэш заземляются на корректность
  content-hash анкоринга. Протечка → уверенные ошибки. Это ядро, не «фича на потом».
- **`asserted`-память** (scratchpad, KB) опаснее `derived`: агент может записать неверный
  вывод и сам же прочитать его как факт. Нужна изоляция уровней доверия и перепроверка против кода.
- **Worktree-изоляция** обязательна для памяти и кэшей — иначе та же болезнь, что кросс-worktree
  баг (ложные факты из чужих worktree).

**Что НЕ делаем сейчас.** Реализацию направлений 3–4 до прохождения гейтов 1–2. Сначала
измеримость и надёжность, затем новые слои.

## Гейты

- **Г1 (Надёжность):** golden-set зелёный на двух реальных проектах; stale-индекс деградирует громко,
  не молча.
- **Г2 (Эффективность):** `bench` показывает регрессии; content-hash кэш даёт измеримое
  ускорение повторных прогонов на неизменном дереве.
- **Г3 (Зона памяти):** на реальной длинной сессии измерено падение расхода токенов от
  дельт/хэндлов; ни одного случая отдачи stale-записи без пометки.
- **Г4 (Мультиязык):** структурный слой работает на не-Swift проекте без регресса Swift-пути.
