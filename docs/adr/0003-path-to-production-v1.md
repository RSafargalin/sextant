# ADR-0003: Путь к продакшн-зрелости v1.0 — порядок закрытия разрыва

- **Статус:** Принято направление (реализация поэтапно, каждый спринт за гейтом)
- **Дата:** 2026-07-22
- **Автор:** Руслан Сафаргалин
- **Связано:** `docs/adr/0001-evolution-to-production-maturity.md` (каталог направлений),
  `docs/adr/0002-mcp-surface.md` (MCP-опора), `docs/roadmap.ru.md` (итерации),
  полевые данные агентской сессии

## Контекст

Полное ревью инструмента (2026-07-22, четыре независимые линзы: архитектура, корректность,
UX/гибкость, тесты) дало вердикт: **ядро зрелое и дисциплинированное** (анти-«тихая
неправота» как сквозной механизм, content-hash кэши, плотное поведенческое покрытие Core,
измерительный контур golden/bench/provenance), **долг сконцентрирован в executable-слое**
и вокруг двойной поверхности CLI/MCP. Четыре major-бага корректности из ревью исправлены
(`changed`/подкаталог, `api`/public extension+protocol, MCP/стейл сниппетов,
`defs`/fallback-определение); 79 тестов зелёные.

Разрыв до «топового продакшн-инструмента» — не в возможностях, а в шести слоях качеств.
ADR-0001 даёт каталог направлений; этот ADR фиксирует **порядок и гейты** доведения до v1.0.

Ключевые факты ревью, определяющие порядок:

- **Двойная поверхность без общего ядра.** Рендер (гистограммы, деградация, context-сводка)
  написан дважды (CLI и MCP) и уже разошёлся; MCP-поверхность имеет три источника истины
  (definitions / instructions / README), которые разъехались (11 vs 9 инструментов).
- **Самый рискованный код — наименее тестируемый.** Оркестрация сборки индекса (выполняет
  чужой `Package.swift`) и весь MCP-протокол живут в executable вне досягаемости тестов:
  1236 строк `main.swift` — ноль тестов, MCP-протокол — ноль тестов.
- **Доказанная ценность не доведена до главного потребителя.** `api --package | grep` дал
  ~79% экономии токенов в полевой сессии, но инструмента `api` в MCP нет; MCP игнорирует
  `.sextant.json`; телеметрия видит MCP-сессию как одну запись.
- **Onboarding требует Swift-toolchain** (`make install`) — главный барьер заявленной
  переиспользуемости на чужой машине.
- **Свежесть индекса — четыре механизма-заплатки** (provenance, `doctor --fix`, `--reindex`,
  re-open в MCP) вместо одного слоя; корневое решение (build-hook) назван в ADR-0001.
- **Однопоточность — скрытое допущение** кэшей; демон `serve` и prefetch его ломают.

## Решение

Шесть направлений в порядке приоритета + операционная зрелость. Правило то же, что в
ADR-0001: каждый спринт за гейтом, без подтверждённой пользы дальше не идём.

### Н1 — Фундамент: одна логика, две поверхности (приоритет: до любого роста)

Не фичи, а условие, без которого каждая следующая фича дорожает.

- **Общий презентационный слой в Core** — рендерер «`SymbolHit`/`SymbolContext` → текст»;
  CLI и MCP — тонкие обёртки. Убирает уже случившийся дрейф форматов.
- **Оркестрация индекса → Core** — зонтичная сборка, xcodebuild-путь, `resolveIndex`-цепочка,
  `percentile`/bench-агрегация выходят из `main.swift` под тесты. В executable остаются
  usage, dispatch, рендер.
- **MCP-инварианты:** `instructions` генерируются из `MCPTools.definitions()`; тест «каждое
  имя из definitions обрабатывается в `callMCPTool`»; Codable-модели tool-definition и
  JSON-RPC конверта вместо `[String: Any]`.
- **E2E smoke-тест MCP-протокола** — спавн бинаря, initialize → tools/list → tools/call →
  resources/read по stdio, коды ошибок. Плюс: false-green интеграционного теста сделать
  видимым (явный skip при отсутствии тулчейна вместо тихого «passed»).
- **Гейт:** `main.swift` ≤ ~600 строк; добавление MCP-инструмента = одна точка правки +
  падающий тест при забытом кейсе; MCP e2e зелёный в CI.
- **Закрыто (П1–П2):** `main.swift` 1257 → 202 строки, executable разбит на связные файлы;
  в Core вынесены `IndexBuild`, `SymbolReport`, `Command`, `Benchmark`; инвариант диспетчера
  и e2e MCP-протокола покрыты тестами (инвариант проверен инъекцией дрейфа); CI на
  GitHub Actions (macOS) гоняет сборку, тесты, self-lint и golden.

### Н2 — Паритет CLI ↔ MCP: довести доказанную ценность до агента

- **`api` как MCP-инструмент** (package/scope/type) — максимальный ROI: переносит
  замеренные ~79% экономии в основной канал. Следом `changed` (символьный дифф — «что я
  сломал» в агентной сессии) и `construct`.
- **Единый конфиг:** MCP уважает `.sextant.json` (budget, rules, scope); битый конфиг —
  громкое предупреждение (stderr + `doctor`), не молчание.
- **Телеметрия per-tool-call в MCP** (инструмент = команда, isError = exit) — иначе
  роадмап-решения принимаются по слепой зоне главного потребителя.
- **Тир достоверности в выводе** — структурный признак `semantic | heuristic | textual`
  в JSON и пометка в тексте: `construct`/`callees`/textual-fallback не должны выглядеть
  как точная семантика. (Опора для «сервиса верификации» из ADR-0001.)
- **Гейт:** типовой полевой сценарий (сбор техсубстрата по 5 типам) проходит целиком через
  MCP без CLI-фолбэка; телеметрия показывает разбивку по инструментам.

### Н3 — Дистрибуция и onboarding: минута до первой пользы

- **Prebuilt-бинарь + Homebrew tap** (universal, notarized) — без Swift-toolchain.
- **`sextant init`** — одна команда: `.sextant.json` + `.mcp.json` + `doctor` +
  предложение собрать индекс.
- **Per-command help** (`sextant map --help`) и **жалоба на неизвестный флаг** — опечатка
  (`--budjet`) сейчас молча игнорируется: тихая неправота в UX.
- **Консистентность поверхности:** `--json` и лимиты для `body`/`construct`/`changed`/`search`;
  синхронизированные README/help/instructions (генерация, не ручная правка).
- **Гейт:** на чистой машине без Xcode-тулчейна: `brew install` → `sextant init` →
  работающий `repo_map` < 5 минут; `doctor` зелёный или каждая ❌ с actionable-фиксом.
- **Сделано (П3):** `sextant init` (конфиг + регистрация MCP без потери чужих серверов +
  проверка setup'а), `CommandCatalog` как источник правды для справки/валидации флагов
  (per-command help, отказ на опечатке с подсказкой, вывод value-флагов), `--json`/`--limit`
  для `body`/`construct`/`changed`, release-workflow с universal-бинарём и формула Homebrew.
- **Остаётся человеку:** создать tap-репозиторий, подставить владельца вместо `OWNER`,
  поставить тег `v0.6.0` и прогнать релиз; добавить LICENSE (иначе `brew audit` ругается).
  До первого прогона гейт «brew install на чистой машине» считается НЕ закрытым.

### Н4 — Скорость: демон `sextant serve` (после actor-изоляции)

Холодные ~2.1с платит каждый CLI-вызов каждого суб-агента — главный налог при агентных
фан-аутах. Unix-socket + тёплый индекс, CLI как тонкий клиент (A1 из ADR-0001).

- **Предпосылка (сначала):** actor-изоляция кэшей (`SourceParseCache`, `PersistentCache`,
  `SourceLineReader`) — однопоточность сейчас скрытое допущение, демон его ломает.
  Заодно закрыть риск общей LMDB-базы IndexStoreDB у параллельных процессов
  (уникальный каталог БД на инстанс, как у sourcekit-lsp) и переместить БД из
  `temporaryDirectory` в `~/Library/Caches/sextant`.
- **Попутно:** in-memory `name→[USR]` мемо (A2) — живёт в демоне естественно.
- **Гейт:** bench: p50 холодного CLI-вызова < 0.3с при живом демоне; деградация без демона
  — прежний путь, не ошибка.
- **Сделано (П4), гейт закрыт:** `sextant serve` (unix-сокет на проект, последовательная
  обработка, клиент использует автоматически, `SEXTANT_NO_DAEMON=1` отключает); замер на
  самом sextant при одинаковом состоянии стора — **2.6с → 0.27с**, p50 ниже порога 0.3с.
  Кэши (`SourceParseCache`, `PersistentCache`) сделаны потокобезопасными на NSLock;
  БД IndexStoreDB переехала из `/tmp` в `~/Library/Caches`.
- **Отклонение от плана (осознанное):** полная actor-изоляция Core НЕ делалась. Она
  потребовала бы асинхронности во всех вызовах ради параллельной обработки, которой у
  последовательного демона нет — самонаведённая сложность. Взято меньшее достаточное:
  последовательный цикл + локи на разделяемых кэшах.
- **Замечено при замерах (вход для Н5):** пересборка проекта меняет index store, и каждый
  следующий процесс переимпортирует юниты (~2.6с). Это ровно та проблема свежести, которую
  build-hook (Н5) убирает в корне; демон её маскирует, но не устраняет.

### Н5 — Свежесть как один слой, а не четыре заплатки

Provenance, `doctor --fix`, `--reindex`, re-open в MCP — четыре механизма в четырёх местах
с краевыми случаями (сигнатура стора смотрит только на первый стор). Корневое решение —
**build-hook** (Iter 9 роадмапа, направление 3.3 ADR-0001): индекс обновляется как побочный
эффект обычной сборки; частичная свежесть по timestamps юнитов (A6).

- Правило до реализации: **новых заплаток на свежесть не добавлять** — признак неверной
  рамки (сложность нарастает вокруг проблемы, убиваемой в корне).

**Рамка Н5 опровергнута экспериментом (П5). Build-hook не нужен.** Замер на живом проекте:
обычная `swift build` **уже** обновляет index store — новый символ резолвится сразу, без
`sextant index`. То есть требование «сделать обновление индекса побочным эффектом сборки»
было выполнено средой изначально; строить хук (или, хуже, watcher) значило решать
несуществующую проблему.

Настоящий дефект был в **сигнале свежести**: он считался по mtime каталога store, а сборка
перезаписывает unit-файлы внутри `<store>/v*/units`, не двигая mtime каталога. Последствия:
- ложные «⚠ STALE» на свежем индексе — маркер обесценивается, а пересборка тратит минуты зря;
- MCP не замечал обычную пересборку (сигнатура стора не менялась) — держал устаревший индекс.

**Сделано (П5), гейт закрыт:** `IndexFreshness` в Core — единственный источник свежести.
Первая версия (максимум mtime unit-файлов с усечением обхода на 50k) была **исправлена по
ревью**: обход десятков тысяч юнитов стоил ~0.5с на КАЖДЫЙ запрос (съедало выигрыш П4), а
усечение давало недетерминированно неверный ответ (порядок записей каталога — не по
времени, свежий unit мог попасть в неосмотренный хвост). Итоговый сигнал — mtime каталога
`units`: O(1), сборка его двигает и при добавлении символа, и при правке файла (проверено).
Введено состояние `fresh/stale/unknown` — «нет данных» (пустой/битый стор) больше не
выдаётся за «свежий» (метка доверия не врёт). По мультистору берётся самый СТАРЫЙ: сборка
одного пакета не делает свежими остальные — ошибаться безопаснее в громкую сторону.
На слой переведены provenance, `indexIsStale`, `doctor`, MCP. Проверено в обе стороны:
правка + обычная сборка → «свежий»; правка без сборки → «⚠ STALE».

**Не делаем:** build-hook и частичную свежесть по timestamps юнитов (A6) — без
подтверждённой проблемы это работа в неверной рамке. Вернуться, если замер покажет, что
переимпорт юнитов после пересборки (~2.6с, маскируется демоном) реально мешает.
- **Гейт:** после обычной `swift build`/Xcode-сборки семантика свежа без ручного
  `index`/`--reindex`; заплатки удалены, а не поддерживаются.

### Н6 — Дифференциаторы («смена лиги», по аппетиту, после Н1–Н5)

Порядок внутри — по ADR-0001/роадмапу (Iter 8–10): зона памяти по content-hash
(хэндлы `ctx://symbol@hash`, регидратация после компакции), context-compiler
(вход — задача, выход — минимальный context-pack под токен-бюджет), мультиязык
(tree-sitter). Без изменений против ADR-0001; этот ADR лишь фиксирует, что вход в Н6 —
только после гейтов Н1–Н3 (Н4–Н5 могут идти параллельно Н6).

**Попытка зоны памяти (2026-07) — отклонена по адверсариальному ревью. Рамка неверна.**
Реализован и откачен кэш производного знания (`context`/`blast`, ключ — `IndexFreshness.
signature`) + хэндлы `sextant://symbol/Foo@<sig>`. Инвалидация работала корректно (замер:
добавление ссылки + пересборка → 11→12, устаревшее не отдаётся). Но ревью вскрыло, что
**рамка протекла**: цель зоны памяти по роадмапу — *падение токенов*, а:
- **кэш токены не трогает** (отдаёт тот же текст) — это машинная микрооптимизация ~0.3с
  CPU на повторном запросе того же символа при той же сигнатуре; в тёплом демоне индекс и
  так открыт, окно пользы узкое и **не измерено**;
- **хэндлы токены ТРАТЯТ**: ~15–20 ток. на каждый ответ, при этом **ни одна инструкция
  инструмента про них не говорит** → агент их не использует → net-negative по той самой
  метрике, ради которой фича существует;
- кэш вносил **тихую неправоту** (D1): `resources/read` не опрашивал индекс перед чтением
  сигнатуры → мог положить данные S1 под ключ S2 и потом выдать их как «свежие»; плюс
  замороженная сигнатура при nil-timestamp (Xcode-раскладка) → бесконечная устарелость.

Признак неверной рамки по CLAUDE.md налицо: **сложность нарастала ради самонаведённой
проблемы** (кэш+хэндлы+детект устаревания хэндла) вместо доказанной пользы. Откачено;
код не сохранён (диздокумент — здесь).

**Что зайти в зону памяти по-честному (порядок):**
1. **Сначала замер, потом код.** В реальной агентной сессии измерить: (а) как часто один
   символ запрашивается дважды при неизменной сигнатуре (окупаемость кэша); (б) сколько
   токенов тратится на *повторную* выдачу того же `context` (потолок пользы от дедупа).
   Без этих двух чисел любая реализация — работа в неизвестной рамке.
2. **Токенную пользу даёт только дедуп-протокол, а не кэш.** Он требует: описание в
   `MCPTools`/`instructions`, чтобы агент возвращал хэндл вместо повторного запроса, и
   замер, что агент этому следует (adoption, ADR-0002). Хэндл без протокола — мёртвый вес.
3. **Кэш — отдельно, как машинная оптимизация**, и только если п.1(а) покажет заметный
   повтор-рейт; тогда с фиксами D1 (poll в `resources/read`), D2 (сигнатура не должна
   замерзать на nil), D3 (prune/eviction в долгоживущем процессе, сейчас только на старте).
4. **asserted-память (scratchpad, cross-session БЗ) — по-прежнему не строим**: подрывает
   анти-«тихую-неправоту».

### Операционная зрелость (сквозное, стартует вместе с Н1)

- **CI на GitHub Actions** (macOS-раннер): build + test + self-lint + golden + bench-регрессии
  на каждый PR. `make ci` остаётся локальным зеркалом.
- **Контракт стабильности:** semver для CLI-флагов и JSON-схем; changelog; фиксированные
  exit-коды (отдельный код для textual-fallback — скрипт должен отличать его от семантики
  без парсинга «⚠»).
- **Безопасность `index`:** предупреждение «выполняет манифест» есть; добавить запуск
  сборки с урезанным окружением (sandbox-exec / чистый env) — инструмент позиционируется
  «на любом чужом проекте».
- **Гигиена переиспользуемости:** маркер `/.claude/worktrees/` в Core — параметром
  с текущим дефолтом; группировка карты, не привязанная к layout `Packages/<X>`.

## Ревью спринтов (2026-07) — что нашло и что закрыто

После П1–П5 проведено адверсариальное ревью каждого спринта независимыми агентами. Итог
важен для честности статусов: **быстрая реализация протащила дефекты, которые тесты не
ловили, потому что рискованный код (демон, свежесть) проверялся мало**. Найдено и
исправлено, с воспроизведением на живом бинаре:

- **Демон, дедлок (critical):** вывод >64 КБ (обычный `api`/`map`) вешал клиента навсегда и
  выводил демон из строя для всех. Дренаж вынесен в Core (`OutputCapture`), покрыт тестом.
- **Демон, чужой проект (critical):** корень резолвил демон в своём каталоге → отдавал карту
  другого проекта с exit 0. Клиент теперь шлёт резолвнутый корень, демон сверяет.
- **Демон, обход запрета сборки (major):** `--reindex` запускал `swift build` по запросу.
  Отклоняется; `SIGPIPE`-смерть от Ctrl-C и захват сокета вторым демоном — тоже закрыты.
- **Свежесть (high):** усечённый обход юнитов давал недетерминированно неверный STALE и
  стоил ~0.5с/запрос — переписано на mtime каталога units (см. Н5).
- **MCP (major):** битый конфиг молча отменял scope; относительный `rules` резолвился не от
  корня; `changed` врал на диапазонных ref'ах и не видел новых файлов, не сравнивал члены типов.
- **Поверхность (high):** `--limit` в справке не работал; `body --json` отдавал текст; `init`
  писал версионный brew-путь (ломался на upgrade).

Вывод для процесса: **тесты на самый рискованный код надо писать адверсариально с самого
начала** (большой вывод, чужой каталог, обрыв связи), а не полагаться на happy-path. Ложно-
зелёный регресс-тест дедлока (воспроизводил свою же логику вместо вызова кода) — тот же урок.

## Открытые вопросы (не закрыты кодом)

- ~~**CI ни разу не запускался.**~~ **Закрыто (2026-08).** Репозиторий опубликован, CI гоняется
  на каждый PR (`macos-26`), релизный workflow отработал на 0.7.0, 0.8.0 и 0.8.1. Гейт Н1 «MCP
  e2e зелёный в CI» закрыт. Попутно нашлось, что зелёный CI не означал проверенного кода: тесты
  C-семейства пропускались, потому что фикстура не была собрана и проиндексирована, — теперь это
  отдельный шаг до тестов, и в прогоне ноль пропусков.
- **Гейт Н3 закрыт наполовину.** `brew install` из tap проверен на машине **с** тулчейном:
  ставится, работает, `brew upgrade` обновляет. Не проверено главное — машина **без**
  Xcode-тулчейна, где синтаксические команды обязаны работать, а семантические падать внятно.
- **`serve` и MCP не разделяют один процесс с одним индексом.** Демон и MCP-сервер — разные
  процессы; агент через MCP не пользуется тёплым индексом демона. Объединение — отдельная работа.
- **Кэши AST/lint-результатов создаются на вызов**, а не разделяются в демоне: демон греет
  только индекс. Замки на них корректны, но пока защищают неразделяемое — задел под общий кэш.
