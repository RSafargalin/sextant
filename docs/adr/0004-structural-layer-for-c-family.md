# ADR-0004: Структурный слой для C-семейства — через компилятор, не через приближённый парсер

- **Статус:** Принято направление (реализация поэтапно, каждый этап за гейтом)
- **Дата:** 2026-08-05
- **Автор:** Руслан Сафаргалин
- **Связано:** `docs/adr/0001-evolution-to-production-maturity.md` (Направление 5 — мультиязык),
  `docs/roadmap.md` (Iter 10, #36), `docs/benchmarks.md` (методика замеров)

## Контекст

Мультиязычность в роадмапе стояла как «tree-sitter: ObjC + generic структурный слой». При
попытке зайти в неё выяснилось, что задача распадается надвое и половина уже сделана.

**Семантический слой мультиязычен изначально.** Index store пишет всё clang-семейство, а не
только swiftc. После двух исправлений резолвера — селекторы Objective-C (`greetWithName:`) и
определения символов, объявленных в заголовке, — `refs`, `defs`, `callers`, `impls`,
`supertypes`, `hierarchy`, `context`, `blast`, `body` работают по Swift, Objective-C, C и C++,
включая межъязыковые вызовы. Это 10 команд из 21, и нового кода разбора не потребовалось.
`map` и `api` расширены тем же способом — чтением объявлений из индекса.

**Свифтовым остался всякий разбор исходника.** Это шире, чем кажется: помимо очевидных
`search`, `lint` и `changed`, от SwiftSyntax зависят ещё две команды, и на не-Swift они уже
ведут себя неверно (проверено на смешанной фикстуре):

| Команда | Поведение на Objective-C |
|---|---|
| `body` | «Could not extract the body» — `SourceBody` разбирает только Swift |
| `construct` | ищет `Type(` — свифтовую форму; идиому `[[Type alloc] init]` не видит вовсе |

`construct` — тихая неправота: он помечен эвристикой, но на чисто ObjC-проекте вернёт пусто и
будет выглядеть как «мест конструирования нет».

Отдельно: `api` отказывается от заголовков C++, потому что индекс не несёт уровней доступа.
У libclang они есть, и это ограничение снимается тем же решением.

Вопрос ADR: чем разбирать не-Swift, чтобы результат соответствовал планке проекта — «не
выдавать молча неполный ответ».

## Замеры

Решение принято по цепочке измерений, каждое из которых опровергало предыдущее ожидание.

### tree-sitter упирается в препроцессор, а не в качество грамматики

Доля файлов, разобранных без единой ошибки, на реальных библиотеках:

| Грамматика | Репозиторий | Чистых файлов |
|---|---|---:|
| C (организация tree-sitter) | redis | 56% |
| C++ (организация tree-sitter) | fmt | 61% |
| C++ (организация tree-sitter) | nlohmann/json | 69% |
| Objective-C (личный репозиторий) | AFNetworking | 75% |
| Objective-C (личный репозиторий) | SDWebImage | 81% |

Официальные грамматики оказались **хуже** community-грамматики Objective-C. Причина общая:
tree-sitter не выполняет препроцессор, а C и C++ в реальности пронизаны `#ifdef` и
макрогенерацией.

### Своя грамматика этого не чинит

Разбор состава ошибок Objective-C (817 штук): 52% строк содержат макрос или аннотацию Apple —
их конечный словарь грамматика распознать может. Остальное — условная компиляция:

```
- (NSImage *)profileImage {      ← внутри #if TARGET_OS_OSX
@class AFHTTPSessionManager;     ← внутри #if
#if TARGET_OS_IOS || TARGET_OS_TV
```

`#if` с разными объявлениями в ветках нельзя разобрать, не выбрав конфигурацию сборки. Имитация
макрос-осведомлённой грамматики (вырезание словаря Apple перед разбором) дала +10 пунктов на
одной библиотеке и −4 на другой — то есть потолок порядка 85%, и то неуверенно.

### Настоящий компилятор даёт 100%, но только с точными флагами

| Источник флагов | AST построен |
|---|---:|
| Приблизительные (SDK хоста) | 25–35% |
| Флаги другого таргета того же проекта | 45% |
| **Пофайловые из сборки, SPM** (SDWebImage, 73 файла) | **100%** |
| **Пофайловые из лога xcodebuild** (AFNetworking, 15 файлов) | **100%** |

Без флагов clang **хуже** tree-sitter: `#import <UIKit/UIKit.h>` при macOS SDK — фатальная
ошибка, дерево не строится вовсе. С пофайловыми флагами — ни одного отказа.

Промежуточные 35% и 45% были ошибками замера (чужой SDK, чужой таргет), а не свойством clang.

### Флаги уже доступны

- `swift build -v` печатает полный вызов компилятора на каждый файл;
- `xcodebuild` пишет команды в лог **даже когда сборка падает** (проверено на AFNetworking,
  несовместимом с современным iOS SDK);
- обе сборки sextant уже запускает сам в `sextant index` и `index --app`.

Дополнительно в тулчейне Xcode лежат `libclang.dylib` и `sourcekit-lsp` — рядом с
`libIndexStore.dylib`, который инструмент уже грузит динамически.

### Паттерны на AST clang сопоставимы

Приём со Swift — компиляция паттерна с подстановкой сентинела — переносится, но требует
поправки: необъявленный идентификатор убивает выражение целиком (clang семантический). Сентинел,
объявленный как `id`, решает это. Формы совпадают узел в узел:

```
паттерн  [SEXTANT_X save]        цель  [s save]
ObjCMessageExpr 'id'  save       ObjCMessageExpr 'void' save
`-ImplicitCastExpr 'id'          `-ImplicitCastExpr 'Store *'
  `-DeclRefExpr 'SEXTANT_X'        `-DeclRefExpr 's'
```

Неизвестный селектор даёт предупреждение, а не ошибку, — искать можно и то, чего в проекте нет.

> **Поправка по замеру (реализация Э3).** Абзац выше неверен в двух местах, и оба вскрылись при
> первой же попытке скомпилировать паттерн отдельным TU:
>
> - под ARC (`-fobjc-arc`, флаг реальных сборок) неизвестный селектор — **ошибка**, а не
>   предупреждение: `error: no known instance method for selector 'foo:'`;
> - и главное — у такого `ObjCMessageExpr` **пустое имя**. Паттерн теряет ровно то, что ищет,
>   поэтому сопоставлять его не с чем.
>
> Решение: паттерн компилируется **не отдельно, а внутри самого файла**, дописанным к его тексту
> через unsaved-файл libclang (путь и флаги файла сохраняются). Тогда селектор известен ровно
> там, где совпадение вообще возможно, флаги — родные, и один разбор обслуживает обе стороны
> (замер: 0.09с на файл, ноль ошибок).
>
> Единого типа для сентинела при этом нет: `id` не существует вне Objective-C, `void *` ломает
> разрешение перегрузок в C++, `int` не подставляется вместо объекта. Поэтому в один разбор
> дописывается несколько проб (`id`, `int`, `void *`, C++-шаблонная), каждая в своей функции и
> под своим `#if`; берётся первая, внутри которой **нет ошибок** и осталось настоящее выражение.
> Проверка «нет ошибок именно внутри пробы» (по позиции диагностики) обязательна: clang оставляет
> дерево восстановления и после ошибки, а сопоставление с ним дало бы «совпадений нет» для
> паттерна, который на самом деле не скомпилировался.
>
> Цена рамки: проба дописывается на файловом уровне, поэтому имя внутри C++-`namespace` ей не
> видно, а квалифицированное имя даёт другую форму дерева. Такой паттерн получает отказ с
> причиной от clang, а не пустой ответ.

## Решение

**Структурный слой для C-семейства строится на libclang, а не на tree-sitter.**

1. **База компиляции снимается при `sextant index`** — из вербозного вывода сборки, которую
   команда уже выполняет. SPM: `swift build -v`. Xcode: лог `xcodebuild`.
2. **`libclang` грузится динамически из тулчейна**, по образцу `libIndexStore`. Новых
   зависимостей в `Package.swift` не появляется.
3. **Матчер работает по курсорам clang и игнорирует типы**: в паттерне они всегда `id`.
   Сентинелы опознаются по имени, как в свифтовой реализации.
4. **Без базы компиляции команда отказывается вслух.** Разница между 100% и 25–35% — это ровно
   наличие флагов, и пользователь обязан знать, в каком режиме получен ответ. Молчаливый поиск
   с плохими флагами нашёл бы треть и выглядел бы полным.

**tree-sitter отвергнут.** Не по стоимости — она оказалась мала (+0.3 МБ в архиве, хотя релизная
сборка втрое дольше), — а потому что 56–85% не проходят планку проекта ни в чьём исполнении.
Своя грамматика тот же потолок наследует.

## Последствия

**Плюсы.** Покрытие компилятора вместо приближения. Выигрыш шире исходной задачи: помимо
`search`, `lint` и `changed` чинятся `body` и `construct` для не-Swift и снимается отказ `api`
по заголовкам C++.

> **Поправка по реализации Э5 — `changed` по C-семейству сделан.** Рамка «текст произвольной
> ревизии разобрать нечем» опровергнута замером: флаги описывают, как файл собирается **сейчас**,
> и этого достаточно — текст старой ревизии, поданный через unsaved-файл на текущих флагах,
> разбирается без единой ошибки (0.19с), список объявлений точен. Это тот же приём, что и у
> поиска: текст из памяти, флаги из сборки. Отказ остался ровно там, где ответа быть не может:
> файл без флагов (не собирался или добавлен после сборки) и ревизия, которая не разбирается, —
> оба называются с причиной. Дифф-алгоритм не дублировался: он работает на `[Declaration]` и был
> языконезависимым с самого начала.

> **Поправка по реализации Э4.** Из четырёх обещаний этого абзаца через clang сделаны три:
> `search`, `lint` и `api` по C++ (`body` был закрыт раньше ограничителем, без clang).
>
> **`construct` сделан не через clang, а языковыми формами.** Команда объявлена эвристической и
> читает строки, на которые указывает индекс; ей нужна не точность дерева, а знание того, что
> в Objective-C объект создают посылкой `alloc`/`new`, а не вызовом типа. Разбор каждого
> ссылающегося файла ради этого — сложность ради самонаведённой задачи. Попутно закрыта
> доэтапная неточность: подстрока `Store(` срабатывала внутри `makeStore(`, теперь форма обязана
> начинаться с границы слова.
>
> **`api` по C++ оказался хуже, чем описано в контексте.** Заголовок не отказывался целиком:
> индекс отдавал его свободные функции (записанные как C) и молча терял все классы — то есть
> поверхность выглядела полной. Теперь заголовок с любым C++ читается через clang целиком
> (уровни доступа `clang_getCXXAccessSpecifier`, приватные члены не попадают) — или не читается
> вовсе, и тогда называется с причиной. Заголовок доступен через любую единицу трансляции,
> которая его включает; флаги для самого заголовка не выдумываются. Ни одной новой зависимости: libclang уже в
тулчейне, а требование Xcode-тулчейна для семантики заявлено с самого начала. Захват флагов
переиспользует сборку, которая и так запускается.

**Издержки и риски.**
- Захват специфичен для системы сборки. Формат лога `xcodebuild` — не контракт и может
  измениться; это хрупкая часть, и она требует теста на живом проекте, а не только на фикстуре.
- Появляется артефакт с временем жизни: база компиляции устаревает так же, как индекс, и обязана
  подчиняться тому же слою свежести (`IndexFreshness`), а не заводить свой.
- Матчер по курсорам — вторая реализация сопоставления рядом со свифтовой. Общий алгоритм с
  разными адаптерами предпочтительнее, но не любой ценой: свифтовый путь на SwiftSyntax даёт
  100% и его перф замерен, регресс там недопустим.

**Что НЕ делаем.** Не пишем свою грамматику. Не поддерживаем структурный слой для языков, где
базу компиляции взять неоткуда: без флагов ответ неполон, а неполный ответ здесь хуже отказа.

## Гейты

- **Г-1 ✅, с уточнением, которое дал живой проект.** На фикстуре совпадение точное:
  `grep -c -o "\[self ocFeed\]"` → 2, `sextant search '[$X ocFeed]'` → 2 (34:12 и 34:28), при
  том что получатель в паттерне — дырка, а не текст.

  На SDWebImage (60 файлов `.m`, база компиляции — 75 записей, 31 файл без флагов: это таргеты
  примеров, которые сборка под macOS не трогает) числа **разошлись**: `grep` — 28 вхождений
  `[NSNotificationCenter defaultCenter]`, `search` — 15. Разбор каждого расхождения: все 13
  пропущенных лежат внутри `#if SD_UIKIT`, неактивного в сборке под macOS. То есть ответ верен —
  но он про **конфигурацию, в которой файл собран**, а не про текст файла.

  Это следствие самой рамки: препроцессор — причина, по которой tree-sitter отвергнут, и он же
  сужает ответ. Формулировка гейта «точь-в-точь как grep» для C-семейства неверна и заменена на
  «совпадает с grep в пределах собранной конфигурации». Ответ теперь называет эту конфигурацию
  строкой `ℹ … were read as built for <triple> — code in inactive #if branches is not part of
  that build and is not searched.`, иначе более узкое покрытие выглядело бы полным.

  Латентность на том же проекте: 13.3с на 75 файлов вхолодную (прогрев кэша модулей clang),
  6.9с повторно. Кэш результатов по content-hash для C-семейства НЕ делается: у файла есть ещё
  и заголовки, изменение которых меняет дерево, — кэш по хэшу одного файла отдавал бы
  устаревший ответ. Возвращаться сюда — только с замером, показывающим, что это мешает.
- **Г-2 ✅:** без базы компиляции команда отказывает с actionable-сообщением; ни одного ответа,
  посчитанного по приблизительным флагам. Отказ пофайловый и с причиной: «нет флагов — соберите
  индекс», «паттерн здесь не компилируется: <диагностика clang>», «заголовок не единица
  трансляции».
- **Г-3 ✅:** свифтовый путь без регресса. Матчер на SwiftSyntax не менялся (вынесена только
  подстановка метапеременных, общая теперь для обоих движков, тесты зелёные); добавленная на
  чисто свифтовом проекте работа — два обхода `git ls-files`, 0.075с.
- **Г-4:** захват флагов проверен на живом Xcode-проекте, а не только на SPM-фикстуре.
  **Не закрыт:** SPM-путь работает, сборка Xcode графа не пишет, и `index --app` об этом
  предупреждает вслух.

## Урок процесса

За время подготовки этого решения замер трижды опроверг ожидание: стоимость tree-sitter
оказалась мала (ожидалась большой), официальные грамматики — хуже community, а главное
препятствие «недели интроспекции сборки» свелось к grep по выводу уже выполняемой сборки.

Отдельно: два промежуточных результата (35% и 45%) были дефектами измерения, а не свойствами
инструмента. Замер требует такой же адверсариальной проверки, как код, — иначе он производит
уверенные неверные числа, то есть ровно то, против чего инструмент и построен.
