# Roadmap — sextant

[English](roadmap.md) | **Русский**

Путь строится итерациями по возрастанию ценности: сначала снять главный технический
риск дёшево, затем наращивать. Каждая итерация самостоятельно полезна и закрывается
**гейтом** — без подтверждённой пользы дальше не идём.

- **Обновлено:** 2026-07-22
- **Решение:** вариант B (переиспользуемый инструмент, отдельный продукт).
- **Стратегия зрелости:** `docs/adr/0001-evolution-to-production-maturity.md` — направления
  развития до продакшн-уровня (надёжность, оптимизация, кардинально новые слои, зона памяти).
- **MCP-поверхность:** `docs/adr/0002-mcp-surface.md` — какие примитивы MCP поддержаны Claude Code
  и переживут stateless-переход (на что опираемся, что игнорируем).
- **Путь к v1.0:** `docs/adr/0003-path-to-production-v1.md` — порядок и гейты закрытия разрыва
  до продакшн-зрелости (по ревью 2026-07-22); спринты П1–П5 идут ПЕРЕД Iter 8–10.

## Северная звезда

```
sextant (Swift package: CLI + MCP server)
  L1 repo-map   — символьная карта под token-budget    (SwiftSyntax/tree-sitter)
  L2 structural — замена grep, структурный поиск        (ast-grep)
  L3 semantic   — defs/refs/callers/callees/public-API  (IndexStoreDB + sourcekit-lsp)
  L4 MCP        — tools + resources для Claude Code      (stdio, .mcp.json)
  L5 (позже)    — свежесть-автоматизация, мультиязычность
```

## Итерации

### Iter 0 — Спайк (выбрасываемый). Снять главный риск. ✅ ПРОЙДЕНО (2026-06-28)
Доказать на проекте A: headless-чтение index store через IndexStoreDB даёт точный
find-references; решить детерминированный `-index-store-path` (убрать зависимость от
хэшей `DerivedData/<Project>-*`).
- **Гейт:** `refs <symbol>` точен и воспроизводим. **Результат — выполнено:**
  `sextant spike --symbol Record` → struct `s:7AppCore6RecordV`, def `Record.swift:6:15`,
  **211** использований; `AggregatedRecordRepository` → 2 использования, кросс-модульно.
  Сверено с исходниками (L3): определения, kind и колонки совпадают; ложных срабатываний нет.
  Авто-обнаружение `libIndexStore.dylib` (через `xcrun`) и свежего DataStore — без конфига.
- **Реализовано:** `IndexStore`, `DerivedDataLocator`, `SourceLocation`/`SymbolHit` (остаются как
  seed слоя L3); CLI-команда `spike` (будет заменена на `refs`/`defs` в Iter 2).
- **Перенесено в Iter 1/2:** *детерминированный собственный* index store через
  `swift build --enable-index-store -index-store-path` (сейчас спайк читает DerivedData-store
  от последней сборки Xcode — доказывает запрос, но не пайплайн свежести).

### Iter 1 — CLI MVP: карта + структурный поиск. Кросс-проектный, shippable. ✅ ПРОЙДЕНО (2026-06-28)
`sextant map --project <path>` (token-budget карта) и `sextant search <pattern>` (ast-grep).
Дёшево, низкий риск, польза сразу.
- **Гейт:** запустить на проекте A **и** на втором проекте; «где начать» отвечается без grep.
  **Результат — выполнено:**
  - `map` на проекте A (несколько пакетов + app-таргет, пара сотен файлов) → полная карта; голова карты сразу
    показывает точки входа (`LiveAppDependencies`, `AppMain`, `ContentView`) — без grep.
  - `map` на самом `sextant` (второй корень) → полный режим, кросс-проектность подтверждена.
  - Token-budget деградирует: полный → компактный → усечение с подсчётом опущенного.
  - `search` реализован как ast-grep wrapper с graceful-деградацией (подсказка, если не установлен).
- **Реализовано:** `SwiftDeclarationExtractor` (SwiftSyntax, build-independent), `RepoMap`
  (обход + группировка по пакетам + рендер с бюджетом), `Declaration`/`FileSummary`; команды
  `map`, `search`. Тесты на экстрактор (9 тестов суммарно зелёные).
- **Полировка на потом (не блокирует гейт):** ignore-globs (сейчас `docs/templates/*.swift`
  попадают в карту как группа `docs`); ранжирование PageRank по ссылкам (сейчас навигация
  по пакету/файлу, бюджет режёт по доступу); исключение `Package.swift` из карты.
- **ast-grep:** для живого `search` нужен `brew install ast-grep` (пока не установлен).

### Iter 1.5 — Свой структурный движок (вариант B). ✅ ПРОЙДЕНО (2026-06-28)
Замена внешнего ast-grep на нативный движок на SwiftSyntax. Метапеременные через
подстановку-сентинел (`$X` → валидный идентификатор, при матчинге = wildcard со связыванием).
- **Реализовано:** `PatternSearch` (компиляция паттерна + структурный матчинг по AST с
  игнорированием тривиа), `StructuralMatch`, общий обход `SwiftSources`. Команда `search`
  переведена на движок; зависимость ast-grep убрана.
- **Гейт:** `sextant search '$X.current'` на проекте A → 13 совпадений, **точь-в-точь как grep
  (13=13)**, но структурно (форма `expr.current`, не текст). 13 тестов зелёные.
- **Поддержано:** одиночные `$X` (выражение-позиция), консистентность повторных имён.

### Iter 1.6 — Вариадик + движок правил гигиены. ✅ ПРОЙДЕНО (2026-06-28)
Достройка движка до вариадика и точной AST-замены regex-гигиены.
- **Реализовано:** вариадик `$$$` / `$$$Name` (поглощает любое число элементов списка, prefix+suffix),
  `Rule`/`RuleViolation`, `RuleEngine` (встроенные правила + загрузка из JSON через `--rules`),
  команда `lint`.
- **Гейт (L3, сверено с grep):** `lint` на проекте A → десятки нарушений: `system-state` 13
  (`.current`), `force-try` 39 (= grep `try!` 39), `print-call` 0. Точь-в-точь, без ложных
  срабатываний. 17 тестов зелёные.
- **Ценность:** `sextant lint` = переиспользуемый AST-чекер гигиены, точнее regex-скрипта;
  правила конфигурируются JSON-файлом на проект.
- **Отложено:** паттерны-statement (`guard … else`), именованные вариадики со связыванием,
  rewrite/codemod.

### Iter 2.1 — Семантические команды. Дифференциатор. ✅ ПРОЙДЕНО (2026-06-28)
`refs`/`defs`/`callers` (IndexStoreDB) + `api` (синтаксис, build-independent). Версия 0.2.0.
- **Реализовано:** `SymbolQuery` (definitions/references/callers по ролям индекса), команды
  `refs`/`defs`/`callers` (продуктизация спайка), `PublicAPI` + команда `api`. Фильтр
  не-системных символов (иначе `Record` коллизирует со SwiftUI). Чистка сигнатур в `api`.
- **Гейт (L3):** `defs Record` → AppCore/Models/Record.swift:6:15; `refs Record` → 211;
  `api --package AppFeature` → публичная поверхность. 19 тестов зелёные.
- **Известные нюансы:** `callers` по конкретному USR не ловит вызовы через протокол/динамическую
  диспетчеризацию (идут на требование протокола); перегрузки разбиваются по USR. `callees` отложен.
- **Перенесено в Iter 2.2:** детерминированный собственный store через `swift build
  --enable-index-store` (сейчас читается DerivedData от последней сборки Xcode — есть лаг свежести).

### Iter 2.2 — Детерминированный index store. ✅ ПРОЙДЕНО (2026-06-28)
Собственный store через сборку, без зависимости от Xcode. Версия 0.2.1.
- **Находка:** у `swift build` НЕТ `--index-store-path`; `--enable-index-store` кладёт store в
  `.build/<triple>/debug/index/store` (детерминированно, по store на пакет).
- **Реализовано:** команда `index` (`swift build --enable-index-store` по всем SPM-пакетам:
  корень + `Packages/*`), `IndexStoreLocator` (поиск пакетов и сторов), `IndexStoreSet`
  (объединение N сторов с дедупом по USR и позиции — для многопакетных проектов). Резолв
  store: `--index-store` → SPM-сторы проекта → DerivedData (fallback).
- **Гейт (L3):** на самом sextant — `index` собрал store в `.build/.../index/store`;
  `refs RepoMap` → def `RepoMap.swift:5:13` + 2 использования, из SPM-стора (НЕ Xcode).
  21 тест зелёный. (Union на проекте A отрабатывает при `index --project <корень A>` — несколько пакетов.)

### Iter 2.5 — Hardening (по анализу состояния). ✅ ПРОЙДЕНО (2026-06-28)
Подготовка к MCP: латентность, кэш, тесты, де-риск масштаба. Версия 0.2.2.
- **`SourceParseCache`** (Core) — кэш AST по mtime; проведён через map/api/search/lint.
  В одном вызове — парс файла один раз; в долгоживущем процессе (MCP) греет AST между запросами.
- **Фикс `lint`** — парс файла один раз на все паттерны: **38.7с → 18.4с** (остаток — матчинг
  5 паттернов отдельными обходами; добивается одиночным обходом-мульти-паттерн — отложено).
- **Стабильный путь БД индекса** — переиспользование между запусками: `refs Record`
  **2.1с холодный → 0.22с тёплый** (10×; критично для MCP).
- **Тесты** на `IndexStoreSet.merge` (union/дедуп), `RepoMap` (бюджет/деградация), кэш. 26 тестов.
- **Де-риск проекта A (реальный прогон всех пакетов, 6 мин):** `index` собрал сторы; нашёл и
  починил **двойной счёт union** разнокорневых сторов (DD из другого checkout, чем SPM) —
  резолв вернул к «SPM если есть, иначе DerivedData» (единый корень → чистый дедуп);
  `refs Record` 416→214.
- **Union дублей НЕ даёт (L3, версия 0.2.3):** все 214 ссылок `Record` уникальны (`uniq -d` пусто),
  единый корень. Прежняя оценка «~5% дубль» была ОШИБКОЙ сравнения (214 SPM-пакеты vs 202
  DerivedData — разные scope, не дубли). «Определение дважды» — артефакт вывода `defs`
  (печатал def-заголовок + то же вхождение), исправлено. Добавлены флаги `--full-paths`, `--limit`.
- **Известные ограничения:** (1) SPM-индекс покрывает пакеты, НЕ app-таргет xcodeproj
  (app — через DerivedData / отдельную индексацию app, план); (2) `lint` всего проекта ~18с
  (агент линтует точечно).

### Pre-MCP спринт — все не-MCP обещания закрыты (v0.5.6, done)
Семь пунктов «качественно и надёжно, без компромиссов» перед MCP:
1. **Транзитивный call-hierarchy** (`hierarchy --callees/--callers --depth N`) — рекурсия по
   IndexStoreDB relations, cycle-detection, дерево + `--json`.
2. **callers через протокол-диспетчеризацию** — учёт relation `.overrideOf`. Попутно крупный фикс:
   **метод-резолв** (имена в индексе с argument-labels `parse(_:referenceDate:)`) — раньше
   refs/defs/callers/callees молча не работали для функций (типы скрывали баг).
3. **PageRank repo-map** (`map --pagerank`) — граф ссылок из индекса → центральность файлов.
4. **`--reindex`** — пересборка индекса перед запросом (свежесть на сборку).
5. **App-таргет** (`index --app`) — xcodebuild + `COMPILER_INDEX_STORE_ENABLE`, автодетект схемы;
   покрывает символы app-таргета, которых нет в SPM-индексе (L3: `refs LiveAppDependencies`).
6. **Дистрибуция** (`make install`) — release-бинарь в `~/.local/bin`.
7. **Интеграционные тесты ядра** — фикстура-мини-пакет: build → index → defs/impls/refs на
   реальном IndexStoreDB (закрыт аудит-P0). 50 тестов, `make ci` зелёный.

### Iter 3 — MCP-обёртка. Интеграция с Claude Code. (v0.5.11, ✅)
Реализовано: `sextant mcp` — stdio MCP-сервер (JSON-RPC 2.0, spec 2025-06-18), последовательный
цикл (один клиент → без concurrency-хазардов), прогретый `IndexStoreSet` при старте. **9 инструментов:**
`context` (headline — сводка по символу одним вызовом вместо серии grep), `who_defines`,
`find_references`, `find_callers`, `list_implementations`, `call_hierarchy`, `repo_map`,
`structural_search` (паттерн по AST — замена grep), `lint`. Контракт — в Core (`MCPTools`), тест.
**Live-свежесть:** `listenToUnitEvents`=true + `pollForUnitChangesAndWait` перед каждым вызовом →
подхватывает реиндексацию без рестарта. L3: initialize/tools-list/tools-call/ping/notification/
error-paths проверены. Регистрация: `claude mcp add` / `.mcp.json` (README).
Параллельно закрыт **edge bare-name** (parse/validate): resolveOccurrences коротко-замыкался на
`canonicalOccurrences(ofName:)` — один нерелевантный точный символ скрывал методы; фикс — всегда
префиксный поиск с фильтром `== name || name(`.
- **Гейт (осталось):** в живой сессии агент берёт MCP вместо grep; замерить падение grep.
- **Дальше по аппетиту:** resource `repo_map` с подпиской; PageRank-веса/функции; мульти-проект (Iter 4).

## Forward-план (Iter 4+) — к продакшн-зрелости

Источник: брейншторм 2026-06-29, `docs/adr/0001-evolution-to-production-maturity.md`
(направления) и `docs/adr/0002-mcp-surface.md` (опора на MCP). Порядок по leverage/cost:
**сначала измеримость и доверие, затем эффективность, поверхность, память, стратегический слой.**
Зависимости явные: память (Iter 8) опирается на content-hash (Iter 5) и Resources (Iter 7).
В скобках — номера из консолидированного бэклога (48 пунктов).

**Статус 2026-08-07:** Iter 4–5 реализованы, Iter 6–7 — частично (см. пометки ниже);
остатки Iter 6–7 и порядок дальнейшего движения — спринты П1–П5 в **ADR-0003**,
Iter 8–10 идут после них.

Два пункта с тех пор ушли из Iter 10 — не отложены, а сделаны:

- **Мультиязык (#36) сделан** — [ADR-0004](adr/0004-structural-layer-for-c-family.md) закрыт по
  всем четырём гейтам. `search`, `lint`, `changed`, `api` и `construct` читают Objective-C, C и
  C++ через clang, на флагах, снятых из сборки (граф SwiftPM или лог `xcodebuild` для проекта
  Xcode). Проверено на SDWebImage из обеих систем сборки: одни и те же 15 структурных совпадений
  плюс 13 текстовых в ветках `#if`, которых нет в сборке.
- **Метрика adoption (#41) сделана** — отдельной командой `adoption` и хуком, а не внутри
  `bench`. Осталось не написание кода, а время: число имеет смысл читать после настоящих сессий с
  подключённым MCP-сервером. Хук подключён 17.08.2026 — до этого он был выпущен, но не стоял ни в
  одном `settings.json`, поэтому отсчёт идёт с этой даты, а не с релиза.

Открытым это оставляет, по порядку: правку классификатора навигации, без которой доля adoption
смещена в нашу пользу (см. «Уроки чужого трекера»); тюнинг описаний (#39) и подсказку вместо grep
(#40) — оба ждут данных, а данные ждут правки; prompts-слэш-команды (#30) и elicitation (#31);
вторую половину гейта П3 (`brew install` на машине без Xcode-тулчейна); три вопроса про демон
(см. Iter 6).

### Iter 4 — Измеримость и доверие. Фундамент. ✅ РЕАЛИЗОВАНО (v0.6.0)
Нельзя оптимизировать неизмеряемое и нельзя называть «лучшим» инструмент с тихой неправотой.
- **`sextant bench`** — фиксированный набор запросов → p50/p95 латентности, peak RSS,
  **счётчик токенов вывода**; в CI ловит перф-регрессии (#14).
- **Golden-set** — `символ → ожидаемые refs/def` на двух реальных проектах в CI, ловит молчаливые
  семантические регрессии (#4).
- **Provenance в ответах** — пометка свежий/stale/синтаксический fallback (#1).
- **Громкая stale-деградация** — не отдавать молча правдоподобно-неполное (#2).
- **Cross-check** семантики со структурным слоем — расхождение = флаг (#3).
- **Корректность семантики:** bare-name требования протокола (#47), мульти-стор дедуп (#48).
- **Гейт:** golden зелёный на двух проектах; stale ни разу не отдаётся без пометки; bench в CI.
- **Факт:** bench, golden (детерминированный тир на фикстуре в CI + CLI-режим `--spec`),
  provenance, громкая деградация, cross-check — реализованы. Остаток гейта: bench-регрессии
  в настоящем CI (GitHub Actions — операционная зрелость ADR-0003).

### Iter 5 — Эффективность ядра (content-hash). Крупнейший машинный выигрыш. ✅ РЕАЛИЗОВАНО (v0.6.0)
Один архитектурный ход (content-hash) закрывает скорость + инкрементальность + кросс-worktree.
- **`git ls-files`-обход** вместо FileManager (C-скорость, полный gitignore); **попутно чинит
  кросс-worktree дубли в refs** (#7, #46).
- **Кэш парсинга по content-hash** (не mtime — хрупок к checkout/worktree/stash); `map`/`lint`/
  `search`: O(все файлы) → O(изменённые), персистентно между запусками (#8).
- **In-memory `name→[USR]`** индекс — повторные lookup O(1) (#6).
- **Гейт:** повторный `lint`/`map` на неизменном дереве — субсекундный; кросс-worktree дубли на
  проекте Б исчезли (сверено); bench показывает ускорение.
- **Факт:** git ls-files-обход (#7), content-hash кэши map/api/lint/search (#8), кросс-worktree
  (#46) — реализованы. **Не сделан #6** (in-memory `name→[USR]`) — перенесён в демон (Н4/П4
  ADR-0003), где живёт естественно.

### Iter 6 — Демон + токенная эффективность. Скорость + метрика, что платит. ⚠ ЧАСТИЧНО

- **Адаптивная многословность** — MCP компакт / TTY читаемо по isatty (#11).
- **Гистограмма вместо списка** — «55 использований: 3 ext, 12 call-sites, 40 аннотаций» (#12).
- **Дедуп строк + детерминированный порядок** (→ prompt-cache модели) (#13).
- **Гейт:** bench фиксирует падение токенов вывода на типовых запросах; cold-CLI снят.
- **Факт:** токенная часть сделана — isatty-многословность (#11), гистограмма (#12), дедуп (#13).
  **`sextant serve` (#5) сделан** — П4 ADR-0003 закрыт вместе с предпосылкой (actor-изоляция
  кэшей). Остались три вопроса, каждый проверен в коде: MCP-сервер держит собственный

### Iter 7 — MCP-поверхность + adoption. На перепроверенной базе ADR-0002. ⚠ ЧАСТИЧНО
Только примитивы, поддержанные Claude Code и переживающие stateless-переход.

- **Prompts как слэш-команды** без required-аргументов: `/feature_map`, `/impact` (#30).
- **Elicitation** через абстракцию (под будущий SEP-2322): «индекс устарел — пересобрать?»,
  дизамбигуация (#31).
- **Tool-аннотации `readOnlyHint`** + простой `outputSchema`; долгая сборка НЕ inline-tool (#34, #35).
- **Adoption-механика:** тюнинг описаний инструментов (#39), перехват/подсказка grep (#40),
  метрика adoption (#41) — сделана отдельной командой `adoption`, а не внутри `bench`: bench
  меряет латентность на фиксированном наборе запросов, а adoption — свойство сессии, вопросы
  разные и общего у них ничего; **`sextant init`** одной командой (#37); prebuilt/Homebrew (#38).
- **Гейт:** ресурсы доступны через `@`; метрика adoption (доля поисков через sextant) растёт;

  и подсказка вместо grep (#40) — оба ждут данных adoption, а данные ждут правки классификатора
  (см. «Уроки чужого трекера»).

### Iter 8 — Зона памяти (code-anchored). Слой разгрузки контекста.
Опирается на content-hash (Iter 5) и Resources (Iter 7). Авто-инвалидация по анкору — то, что
отличает её от опасной generic-памяти.
- **Mmap «дайджест проекта»** (символьная таблица + граф) — query-optimized субстрат (#10).
- **Память-по-указателю** — хэндлы `ctx://symbol@hash` вместо блобов, через resource-links (#23).
- **Кэш производного знания** — call-граф, blast-radius, карта фичи, ключ content-hash (#24).
- **Регидратация после компакции контекста** — точная замена лоссовому сжатию (#26).
- **Архитектура** — anchoring, тиринг hot/warm/cold, eviction LRU+релевантность, provenance
  `derived` vs `asserted`, worktree-изоляция (#28).
- **Фаза 2 (риск asserted):** сессионный scratchpad (#25), cross-session база знаний (#27).
- **Гейт:** на длинной сессии измерено падение токенов от хэндлов/дельт; ни одной stale-записи
  без пометки.

> **Фаза 1 закрыта — замерено, потолка пользы нет (2026-08-08).** По 26 реальным агентным
> сессиям (≈6.1 МБ навигационного контента) три независимых определения «повтора» сходятся:
> тот же вызов с теми же аргументами — **0.9 %** навигационных байт, побайтово идентичный
> результат в одной сессии — **0.5 %**, в более поздней — **0.5 %**, перечитанный неизменившийся
> файл — **5.5 % байт чтений**. Дедуп-протокол отыграет единицы процентов от доли токенов сессии —
> и это до вычета собственной цены хэндлов (~15–20 ток. на ответ). Причина в тех же числах: агент
> редко просит дважды, а перечитывает обычно то, что сам только что изменил, — как раз то, чему
> хэндл служить не может. Трата не в повторе, а в **первой** выдаче: это context-compiler
> (#16, Iter 10), замером не задетый. Обоснование и таблица —
> [ADR-0003](adr/0003-path-to-production-v1.md).
>
> **Второй аргумент, независимый от токенов (2026-08-17).** У Serena отравление памяти между
> проектами заявлено как уязвимость вместе с path traversal в путях памяти
> ([#1251](https://github.com/oraios/serena/issues/1251)). Фаза 2 («риск asserted») получает не
> только сомнительную пользу, но и класс атаки: запись, сделанную в одном проекте, читает другой.

## Уроки чужого трекера — Serena (2026-08-17)

[Serena](https://github.com/oraios/serena) — ближайший аналог по назначению: MCP-тулкит для
навигации и правки кода, 40+ языков через LSP, 28 тыс. звёзд. Прочитан весь трекер: 823 issue,
762 закрытых и 61 открытая. Это не конкурентный анализ, а источник детекторов: чужой баг дешевле
своего.

**Широта — обязательство, а не преимущество.** 332 issue из 823 (40 %) — водопровод конкретных
языков и LSP, а среди открытых таких две трети. Kotlin и Clojure оставляют зомби-процессы, Kotlin
LS засоряет `/tmp`, Bloop переживает `stop()` и перерождается к PID 1, JDT LS не стартует на новой
Java, Erlang LS заархивирован, F# регрессировал. Каждый язык — внешний процесс со своим жизненным
циклом, и это навсегда. Специализация на Apple-среде — отказ от этой ренты, а не сужение рынка.
Вторая по размеру корзина — конфигурация и установка: 213 issue. Отдельно
[#1327](https://github.com/oraios/serena/issues/1327): их собственные тиры поддержки языков
признаны недостоверными, поэтому «Swift в обычном тире» ничего не обещает.

**Подтверждённые тезисы.** Их аварии — ровно то, против чего построен наш слой честности:

- [#1814](https://github.com/oraios/serena/issues/1814): `find_referencing_symbols` вернул `{}`,
  потому что tsserver умер от OOM, — с `isError: false` и логом «cross-file indexing complete».
  Формулировка автора о форме отказа: быстро, уверенно и неверно; агент сделает вывод, что мёртвый
  код можно удалять. [#1593](https://github.com/oraios/serena/issues/1593) — тот же класс: `find_symbol`
  отдаёт устаревшие данные.
- [#576](https://github.com/oraios/serena/issues/576),
  [#326](https://github.com/oraios/serena/issues/326),
  [#1744](https://github.com/oraios/serena/issues/1744): symbolic editing дублирует код, даёт
  синтаксическую ошибку и молча пропускает файлы, которые не открыты, оставляя висячие ссылки.
  Это ответ на вопрос «добавлять ли правки»: у зрелого LSP-инструмента правка молча неверна. Если
  браться — только с гейтом «сборка зелёная после правки».
- [#1325](https://github.com/oraios/serena/issues/1325),
  [#1042](https://github.com/oraios/serena/issues/1042): JSON-вывод потребляется моделью хуже, чем
  структурированный текст. Наша текстовая поверхность с provenance внутри ответа — не отставание.
- [#992](https://github.com/oraios/serena/issues/992),
  [#1607](https://github.com/oraios/serena/issues/1607): к валидации по хешу содержимого они пришли
  после боли; у нас это Iter 5 как архитектурный ход. И
  [#726](https://github.com/oraios/serena/issues/726) «сохранять точный текст источника» — у нас
  бесплатно, потому что читаем файлы, а не только узлы LSP.
- Инъекция команд через `shell=True`
  ([#1585](https://github.com/oraios/serena/issues/1585)): у нас этого класса нет по конструкции —
  везде `executableURL` плюс массив аргументов, ни одного запуска через шелл.

**Найденный у себя дефект.** [#1845](https://github.com/oraios/serena/issues/1845): Claude Code
2.1.117+ на нативных сборках macOS/Linux убрал инструменты `Grep` и `Glob`, отправив их через
`Bash` как встроенные `ugrep`/`bfs`. Наш `NavigationAct` знает `grep, rg, ag, ack, ripgrep` и не
знает `ugrep` и `bfs`. Замер на установленном бинаре: из трёх событий (`ugrep`, `bfs`, `rg`)
записалось одно. Пропадает **знаменатель**, то есть доля sextant выглядит выше реальной, — а на
ней стоят #39 и #40. Правка одна для обоих путей: хук и читатель транскриптов используют один
классификатор.

**Детекторы, которых у нас нет** — каждый из чужих грабель:

- демон убит сигналом → файл сокета не остаётся, следующий клиент не спотыкается
  ([#1464](https://github.com/oraios/serena/issues/1464),
  [#1816](https://github.com/oraios/serena/issues/1816));
- один нечитаемый, огромный или странно названный файл не рушит обход
  ([#514](https://github.com/oraios/serena/issues/514) — падение на `.ico`,
  [#182](https://github.com/oraios/serena/issues/182) — слишком длинное имя);
- семантический слой умер посреди запроса → ответ не пустой без пометки (#1814).

**Взято из их данных.** [#1491](https://github.com/oraios/serena/issues/1491) — замер по 21 089
вызовов, 192 сессиям и 21 дню: Serena участвует лишь в 35,4 % сессий, её доля — 20,3 % операций
чтения. Второй сигнал важнее: **18,4 % символьных запросов заканчиваются обычным `Read` того же
файла**, причём в 80,8 % случаев тело символа уже было в ответе, а `Read` шёл с `offset`/`limit`, —
агент имеет тело и лезет за окружающими строками. Отсюда две задачи: `--context-lines N` у `body` и
`context`; и фолбэк-метрика в `adoption` — «после какого нашего ответа агент всё равно пошёл читать
файл». Второе их скрипт не умеет, а наша команда может: она читает транскрипты целиком.

**Своя тихая неправота, найденная попутно.** MCP-сервер отражает клиенту любую заявленную им
ревизию протокола (по умолчанию `2025-06-18`), то есть подтверждает поддержку того, чего может не
реализовывать.

## Ближайшее — правки, а не ставки

Порядок жёсткий: первое блокирует всё, что опирается на adoption.

1. **`ugrep` и `bfs` в классификаторе** плюс тест на каждое имя инструмента поиска. Без этого доля
   adoption смещена в нашу пользу, и #39/#40 строятся на завышенном числе.
2. **Три детектора из чужих грабель** (список выше): сигнал демону, странный файл, смерть
   семантики посреди запроса.
3. **`--context-lines N` у `body`/`context`** и **фолбэк-метрика в `adoption`** — обе из данных
   #1491.
4. **Честная ревизия MCP** вместо эха клиентской.
5. **`doctor` проверяет цепочку целиком** — сегодня он печатает «✅ ready — sextant mcp will work»,
   не проверяя ни регистрацию MCP в клиенте, ни хук: ровно тот класс дефекта, из-за которого хук
   простоял десять дней незамеченным.

## Кандидаты после 0.9.0 — по осям, а не по номерам

Не итерация, а ставки с разной ценой и разным риском. Порядок внутри оси — по отношению пользы к
цене; порядок между осями решается данными adoption, когда они станут несмещёнными.

**Ось 1. Ответы, которых у LSP-инструмента нет в принципе.** Здесь отстройка, а не догонялки:
конкурентность Swift 6 (пересечения границ `@MainActor`, пробелы `Sendable`, изоляция акторов);
мёртвая публичная поверхность (`api` ∩ `refs` — что `public`, но не используется вне модуля, прямой
инструмент для вынесения модуля); ссылки вне статического графа (`#selector`,
`NSSelectorFromString`, KVO-строки: индекс знает `@objc`-имя, значит строку можно связать с
символом); граф внедрения SwiftUI (`@Environment`/`@EnvironmentObject` — символ, достижимый только
через окружение); `@available` и deployment target (что освободится или сломается при поднятии
минимальной iOS); покрытие символа тестами (какие публичные символы не упомянуты ни одним тестовым
таргетом).

Туда же — четыре ответа, собираемых из уже готовых частей:

- **`api --from <ref> --to <ref>` — диф публичной поверхности с вердиктом semver.** У `changed`
  режим сравнения ревизий есть, но он про все символы, а не про контракт; у `api` сравнения нет
  вовсе. Для автора библиотеки «что я ломаю этим релизом» — главный вопрос перед релизом. В LSP
  понятия «контракт модуля между двумя ревизиями» не существует.
- **`review <range>` — импакт целого PR, а не одного символа:** сколько символов задето, суммарный
  blast, сколько из них публичных, какие без тестов, какие таргеты затронуты. Композиция `changed`
  + `blast` + `api` + границ таргетов — и ровно тот артефакт, который нужен живому ревьюеру. Это
  ось 4 в конкретной форме, без разговора про рамку продукта.
- **Граф импортов и циклы между таргетами** — архитектурная проверка, кормящая вынесение модуля.
- **Владельцы в blast-радиусе** — `git blame` по местам использования: «эту правку стоит показать
  этим двоим». `git` уже под рукой, `blame` не используется нигде.

**Ось 2. Реальность Xcode — единственный настоящий моат.** Workspace из нескольких проектов,
несколько схем и конфигураций одновременно, таргет как понятие первого класса («какие таргеты
сломает эта правка»). В LSP этих понятий нет. Предпосылка — спайк: поставить Serena на эталонный
Xcode-проект и сравнить ответы. Без него утверждение «на `.xcodeproj` мы сильнее» остаётся на L1.

**Ось 3. Дистрибуция и доверие к установке.** Плагин Claude Code одним шагом — MCP-сервер, хук и
слэш-команды в одной установке (закрывает #30 и снимает три ручных шага; у Serena большой запрос
ровно на это — [#802](https://github.com/oraios/serena/issues/802)). HTTP-транспорт: сейчас только
stdio, значит облачные и удалённые сессии до sextant не достают вообще. `make verify-public` — стенд
из пяти публичных репозиториев и `tea` как повторяемый артефакт, а не разовые скрипты: в прошлом
прогоне половина ложных находок была багами самого стенда.

**Ось 4. Гейт в чужом CI — единственная ставка, которая не конкурирует, а обходит.** `lint`, мёртвая
публичная поверхность, запрещённые импорты и границы модулей как проверка PR. Половина
инфраструктуры есть: `golden` (семантические регрессии по спеке) и `bench`. Это делает инструмент
нужным команде, а не только агенту, — и это разговор про рамку продукта, а не задача на вечер.

**Ось 5. Оптимизация — по замеру, а не по ощущению.**

- **Прогрев демона по событию сборки.** Переимпорт после пересборки — ~2.6 с, и он «маскируется
  демоном» только если демон уже жив *и* запрос пришёл позже. Демон может следить за стором и
  переимпортировать заранее: тогда свежесть достаётся бесплатно, а не за счёт первого запроса.
- **`name→[USR]` в памяти (#6)** — единственный неначатый пункт Iter 5. Его перенесли в демон, и
  там о нём забыли; демон теперь есть.
- **Вердикт вместо дампа.** Последняя строка ответа про влияние — вывод, а не список: «12 мест в
  2 таргетах, 1 тест покрывает, публичный контракт не меняется». Дешевле context-compiler (#16) и
  бьёт в ту же трату — первую выдачу, которую замер назвал настоящей.

**Ось 6. Детекторы под собственные грабли.** Мы добавляем детектор на каждый сбежавший дефект; вот
классы, где детектора до сих пор нет:

- **Property-тесты на счёт ссылок.** Багов счёта было минимум четыре: двойной учёт при раскрытии
  макроса, ветки `#if`, позиция, не несущая имени, внутренний предел, поданный как полное число.
  Это худший наш
  класс, и против него только точечные тесты. Нужны инварианты на случайно сгенерированном
  источнике: число позиций равно числу ссылок, ни одна позиция не вне границ файла, дедуп
  идемпотентен.
- **Нагрузочный тест демона** — двадцать одновременных клиентов. Голодание пула потоков мы только
  что чинили; класс живой, теста нет.
- **Golden на настоящем репозитории**, не только на фикстуре: спека для одного из публичных
  проектов ловит молчаливые семантические регрессии на живом коде, чего фикстура не умеет.
- **Неоднозначность имени** — что делаем, когда имя принадлежит нескольким USR, и как агент
  выбирает стабильно. Обработки в отчёте не нашлось (L1, нужен просмотр кода).

**Ось 7. Мелочи честности и процесс.**

- **Каждый отказ называет следующую команду** — местами это уже так («build the index:
  `sextant index`»), но как правило с тестом — нет.
- **`--explain`** — след решения: какой стор, почему, покрытие, что отброшено. Provenance у нас
  одна строка; полный след нужен и доверию, и отладке.
- **Побайтовая стабильность вывода при повторе** — дедуп и детерминированный порядок (#13) сделаны
  ради prompt-cache модели, но что они не сломаются, ничем не закреплено.
- **Механизм леджера в AGENTS.md** — `withKnownIssue` (зелено, пока дефект жив; падает в момент
  починки) закрыл 24 дефекта и нигде не описан как стандарт работы.
- **`adoption` замыкает #39** — сама предлагает, какое описание инструмента менять, исходя из формы
  запросов, ушедших мимо нас.

## Бэклог — ждёт обстоятельств, а не работы

Здесь нет пунктов, заблокированных решением или чьим-то кодом. Каждому нужно, чтобы сначала
что-то случилось в мире, — поэтому они лежат тут, а не поднимаются на каждом планировании.

- **Вторая половина гейта П3: `brew install` на машине без Xcode-тулчейна.** Первая половина
  (машина с тулчейном) пройдена. Для второй нужна машина, которой пока нет под рукой; без неё
  утверждение «ставится без тулчейна» остаётся на L1.
- **Данные adoption.** `sextant adoption` читает транскрипты и работает. Хук `PreToolUse` был
  написан и выпущен, но **не был подключён**: десять дней он не стоял ни в одном `settings.json`, а
  сниппет из `hook --install` называл несуществующий бинарник (собирался из `argv[0]`, а это голое
  имя при запуске через `PATH`), — то есть вставка сниппета поставила бы хук, который молча ничего
  не пишет. И то и другое исправлено 17.08.2026: сниппет берёт настоящий путь запущенного бинарника,
  хук стоит в пользовательских настройках, проверено появлением записи в логе. Значит, отсчёт идёт с
  этого момента: сигнал что-то значит примерно после недели обычных сессий, и до тех пор #39
  (описания инструментов) и #40 (перехват grep) не на чем строить — оба меняют поведение, которое
  ещё не измерено.
- **Linux.** Никогда не планировался — ни за, ни против. Семантика — IndexStoreDB (переносима),
  Swift-структура — SwiftSyntax (переносима), C-семейство — libclang через `dlopen` (в принципе
  переносим, но поиск пути написан под Xcode). Открыт не вопрос «насколько сложно», а вопрос
  «кому» — никто не просил.

## Закрыто замером, а не мнением

### Общий каталог базы IndexStoreDB между процессами — вред НЕ подтверждён (2026-08-17)

Каталог базы выводится из пути стора, поэтому все процессы, работающие с одним стором, делят одну
базу. Это числилось дефектом («два процесса молча переимпортируют её»). Замер говорит обратное:
именно общая база и делает одновременную работу дешёвой.

Стенд: стор Xcode эталонного проекта, 22 725 юнитов, 528 МБ; `refs AbsAccountsViewModel`;
`SEXTANT_NO_DAEMON=1`; время на процесс, по часам.

| процессов | одна общая база | по базе на процесс |
|---:|---:|---:|
| 1 | 25.0с | 29.5с |
| 2 | 25.2с | 44.6с (36.2–53.0) |
| 4 | 34.4с | 73.8с |

Контроль здесь важнее самих чисел: раздельные базы получены копированием стора на четыре пути, так
что у каждого процесса свой ключ. Они **хуже на каждом уровне** — четыре отдельные базы по 256 МБ
вытесняют друг друга из страничного кэша, а одно общее отображение читают все четыре.

Что проверено помимо скорости: все прогоны дали один и тот же ответ (`usages: 7 in 3 file(s)`) при
1, 2 и 4 процессах, на холодной базе и на тёплой; запрос после всего прогона отвечает верно; база
осталась в 2 файла и 256 МБ. Ни переимпорта, ни неотпущенной блокировки, ни повреждения.

Один случай всё же стоит денег: запрос CLI, импортирующий холодную базу, пока демон держит тот же
стор открытым, занял 36.5с против 24.7с у того же холодного импорта в одиночку. Случается это один
раз после пересборки, ответ верен, а приписать разницу именно общей базе, а не двум работающим
одновременно процессам, без ещё одного контроля нельзя.

Не проверено: больше четырёх процессов, стор, который Xcode перезаписывает **во время** запросов, и
любая платформа кроме этой. Пункт закрыт как неподтверждённый, а не как исправленный: чинить нечего,
пока один из этих случаев не покажет вред.

## Не-цели v1 (перенесены в forward-план, не вырезаны навсегда)

На старте вырезано осознанно (максимум риска при минимуме пользы), но запланировано позже:
- **vector search** → graph-RAG в Iter 10 (заземлён на граф, не наивные чанки).
- **не-Swift семантика** → **сделано**: работает через тот же index store, отдельного слоя не
  потребовалось. Структурный слой для этих языков **тоже сделан** (2026-08-07) — на libclang, а не
  на tree-sitter, см. [ADR-0004](adr/0004-structural-layer-for-c-family.md).
- **автосвежесть** → **сделано иначе, чем планировалось.** Build-hook не понадобился: обычная
  сборка уже обновляет index store, чинить нужно было сигнал свежести (`IndexFreshness`,
  П5 ADR-0003).

Остаётся не-целью: real-time file-watcher (постоянное слежение за ФС).

## Не-цели после специализации на Apple-среде (2026-08-09)

[ADR-0005](adr/0005-apple-environment-specialisation.md) сужает продукт до Apple-среды — Swift
вместе с Objective-C, C и C++; SwiftPM и Xcode; iOS/macOS/watchOS/tvOS/visionOS — и меняет широту
на стандарт качества внутри неё. Широту держит Serena (LSP, 40+ языков, MIT, живая); Swift-специфичные
конкуренты архивированы или заброшены. Переезжают из «потом» в «не мы»:

- **Языки за пределами Apple-среды** (#36 дальше C-семейства): Rust, Go, Python, Java/Kotlin,
  TypeScript.
- **Linux** — бэкенд семантики привязан к index store и Xcode-тулчейну.
- **Кросс-проектный интеллект** (#22) и **graph-RAG** (#18) — широта другого рода, та же логика.
- **Рефакторинг-as-a-service** (#20) — территория Serena, и он требует отказаться от «только
  чтение», на котором стоит доверие к инструменту.
- **«Негативное пространство»** (#43) остаётся в списке, но **не берётся** без ответа на вопрос
  «чем мы лучше [Periphery](https://swiftpackageindex.com/peripheryapp/periphery)» — семь лет
  разработки на том же index store.

Взамен — глубина: у индекса есть личность (платформа, конфигурация, цели, покрытие), стор
выбирается по покрытию, а не по mtime, `#if` сообщается рядом с семантикой, а не только вместо неё,
и provenance называет сборку, про которую ответ.
